# Chronicle: проектное решение

Chronicle — настольный редактор истории git для macOS, Windows и Linux.

## Принципы

1. **Сначала черновик.** Правки истории копятся в черновике и ничего не меняют, пока пользователь не нажмёт «Применить».
2. **Предпросмотр равен результату.** Предпросмотр создаёт настоящие объекты коммитов, но не двигает ссылки. «Применить» только атомарно переставляет ссылки на уже проверенный результат.
3. **Любое применение обратимо.** Перед применением старые значения сохраняются в `refs/chronicle/backup/*` и в журнале.
4. **Сервер меняется отдельным шагом.** Локальное применение никогда не трогает remote. Force-push выполняется только после подтверждения и только с lease.
5. **Рабочая папка не участвует в переписывании.** Движок работает с объектами git и обновляет файлы только в конце.

## Архитектура

| Слой | Путь | Ответственность |
|---|---|---|
| Ядро | `src/core` | Вся логика git на Node, без Electron, покрыта тестами |
| Общее | `src/shared` | Типы, раскладка графа, наложение черновика |
| Основной процесс | `src/main` | Окно, IPC, диалоги, таймер публикаций |
| Preload | `src/preload` | Узкий мост `window.chronicle` |
| Интерфейс | `src/renderer` | React без доступа к Node |

Ядро вызывает системный git через `spawn` с массивом аргументов, без shell. Минимальная версия git: 2.45, она нужна для `merge-tree --merge-base` с деревьями.

## Движок переписывания

План состоит из правок метаданных, последовательности для линейного участка ветки и списка путей для удаления из истории.

1. Находятся все коммиты-потомки затронутых коммитов во всех локальных ветках и тегах.
2. Коммиты обходятся от родителей к потомкам. Новые объекты записываются из исходных байтов, поэтому нетронутые поля, часовые пояса и даты сохраняются точно.
3. Если родитель сменился, а его дерево то же, дерево коммита остаётся без изменений. Иначе изменения переигрываются через `merge-tree` в памяти.
4. Нетронутый коммит сохраняет свой SHA.
5. Подпись снимается только с изменившихся коммитов, о чём предупреждает предпросмотр.
6. Конфликт или merge-коммит, который нельзя пересоздать точно, блокирует применение. Ссылки при этом не меняются.

`refs/remotes/*` никогда не переписываются. Они показывают состояние сервера, поэтому расхождение остаётся видимым до force-push.

## Работа с удалённым репозиторием

- **Force-push:** перед отправкой проверяется реальная вершина на сервере через `ls-remote`, затем используется `--force-with-lease=<ref>:<ожидаемый SHA>`.
- **Переименование ветки:** новая ветка создаётся из серверной вершины, настраивается upstream, затем старая удаляется с lease. Основную ветку сервера удалить нельзя, пока не сменён default branch, поэтому интерфейс заранее предупреждает об этом.
- **Отложенная публикация:** коммиты сохраняются в `refs/chronicle/scheduled/<id>`, ветка откатывается, а в назначенное время коммиты перекладываются на актуальную вершину и отправляются обычным push. При конфликте публикация останавливается, данные сохраняются.

## Что остаётся видимым после переписывания

История на сервере выглядит так, будто всегда была такой, но полностью следы не исчезают. Старые коммиты остаются в чужих клонах и форках, могут открываться по прямому SHA, а журнал активности сервера фиксирует force-push. Утёкшие секреты нужно отзывать, даже если они удалены из истории.

## Конфликты и разделение

Предпросмотр останавливается на первом конфликте и возвращает версии файла. Ответы пользователя добавляются в план, после чего предпросмотр строится заново, пока конфликты не закончатся. Деревья с ответами и разделённые коммиты собираются через временный индекс, поэтому настоящий индекс и файлы не меняются.

Разделение делит коммит на два: выбранные куски образуют новый коммит под ним, а итоговое дерево остаётся прежним. Если выбранные куски перестали применяться после перестановки, план блокируется.

## GitHub и GitLab

Приложение не входит в аккаунт и не обращается к API серверов. С сервером работает системный git с ключами и настройками этого компьютера. Тип сервера определяется по адресу remote, и от него зависят только ссылки на сайт: запросы, настройки защиты и основной ветки.

Переименование ветки на сервере идёт через git: создаётся новая ветка, затем удаляется старая. Открытые запросы от старой ветки могут закрыться, а основную ветку сервер удалить не даст, пока её не сменят на сайте. Перед таким шагом приложение предупреждает об этом.

## Перенос ветки и pull

Перенос ветки на другую идёт тем же движком, что и правка истории: в участке указывается `onto`, и цепочка коммитов строится поверх него. Коммит, изменения которого в целевой ветке уже есть, пропускается с предупреждением, как это делает `git rebase`. Ветки, которые стояли поверх переносимых коммитов, переезжают вместе с ними.

Pull, когда разошлись обе стороны, по умолчанию предлагает тот же перенос поверх ветки на сервере. Поэтому конфликты решаются в предпросмотре, до изменения рабочей папки. Если в ветке есть merge-коммиты, перенос делает сам git.

Конфликты merge предсказываются через `git merge-tree --write-tree`: он строит итоговое дерево без изменений в рабочей папке и называет файлы с конфликтами.

Предпросмотр сообщает список коммитов, которые он записал (`created`). Значения в карте замен для этого не подходят: удалённый коммит указывает на старый коммит, к которому привязан.

## Доступ к серверу

Вопросы от git и ssh идут через `GIT_ASKPASS` и `SSH_ASKPASS`. Оба указывают на небольшой скрипт, который приложение пишет при запуске. Он запускает само приложение как Node и передаёт вопрос по локальному сокету с одноразовым для запуска токеном. Так работает и macOS, и Windows, где скрипт запускает `sh` из состава Git. Если в настройках git указан системный `ssh` Windows, окно пароля не появится: он не умеет запускать такой скрипт, и подходит только ключ из его агента.

На Windows есть две разные копии ssh с разными агентами. git использует свою, поэтому проверки ключей запускают её же.

Пароль ключа проверяется через `ssh-keygen -y` до передачи в ssh: сам ssh после неверного ответа часто сразу сдаётся. Пароль хранится в памяти 15 минут, чтобы один push не спрашивал его несколько раз. На диск он попадает, только если пользователь выбрал «Запомнить», и только зашифрованным через `safeStorage`. На macOS любой вызов `safeStorage` может показать системное окно Связки ключей, поэтому используются только асинхронные вызовы и только когда пароль действительно сохраняется или читается: синхронные заморозили бы приложение. Новый ключ получает пароль тем же путём, поэтому тот не появляется в командной строке.

Отложенная публикация идёт без вопросов: она может использовать только сохранённый пароль или агент. Если доступа нет, публикация остаётся в ожидании и повторяется сама, а приложение один раз сообщает об этом. Диалог таймера проверяет это заранее.

Помощник сначала подтверждает сам сервер, затем проверяет каждый ключ отдельно через `IdentitiesOnly`. Имя аккаунта берётся из приветствия сервера. Ключ с необычным именем закрепляется за репозиторием через `core.sshCommand`, и только если без этого сервер не открывает репозиторий. Глобальные настройки и `~/.ssh/config` приложение не меняет, а существующие ключи не перезаписывает. Подмена ключа сервера никогда не подтверждается автоматически.

## Языки и тема

Исходный текст интерфейса русский и служит ключом словаря: код вызывает `t('Русский текст')`, а английский перевод лежит в `src/shared/i18n-en.ts`. Тест проверяет, что у каждого текста есть перевод и что в коде не осталось русского текста вне `t()`.

Окно узнаёт язык синхронно до запуска своих скриптов, поэтому переводятся и тексты в константах. Смена языка перезагружает окно, открытый репозиторий при этом сохраняется. Записи журнала и публикаций хранятся на языке, на котором были созданы, и при показе переводятся обратно по тем же шаблонам. Ошибки ядра переводятся основным процессом в момент, когда возникают.

Тема задаётся через `nativeTheme.themeSource`, поэтому CSS следует ей через `prefers-color-scheme`, а системные окна меняют тему вместе с приложением.

## Подпись

Предпросмотр никогда не запускает подпись, чтобы не спрашивать пароль ключа без причины. При применении переписанный коммит, у которого была подпись, подписывается через `git commit-tree -S`, поэтому работают настройки пользователя. Результат сверяется с нужным коммитом побайтно. Если git не смог воспроизвести его точно, коммит записывается без подписи, а предпросмотр сообщает об этом.

## Этапы

1. **Готово.** Просмотр истории, базовые операции, stash, ветки, правка метаданных, перестановка, squash, удаление, откат, force-push, отложенная публикация, удаление файла из истории.
2. **Готово.** Разрешение конфликтов в интерфейсе, разделение коммитов, staging отдельных кусков, установщики.
3. **Готово.** Автозапуск. Вход в аккаунты GitHub и GitLab был сделан на этом этапе и позже убран.
4. **Готово.** Переподпись коммитов, проверка обновлений, черновики выпусков.
5. **Готово.** Работа без входа в аккаунт: окно пароля ключа, поиск, проверка и создание SSH-ключей, подсказки по добавлению ключа на GitHub и GitLab, автор коммитов для репозитория.
6. **Готово.** Перенос ветки на другую с предпросмотром результата, merge и pull с предсказанием конфликтов, поиск по изменениям, история файла и blame, worktree, submodules, LFS, сборка для Linux.
7. **Готово.** Английский интерфейс и выбор языка, переключатель светлой и тёмной темы.
8. Подпись установщиков и автоматическая установка обновлений. Для них нужны платные сертификаты. ИИ-подсказки для сообщений и разделения.
